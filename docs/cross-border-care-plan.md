# Avenlio Care 跨境就医网站完善规划

制定日期：2026-10-29。品牌为 Avenlio Care（安诺医伴）；首批公开目录仍为北京、天津，不将服务地域写入品牌名。

## 1. 产品定位与完成标准

第一版负责帮助海外用户了解公开资源、整理咨询、明确服务范围并进行人工协调。医院负责接诊决定、诊疗意见、手术适应证、医疗报价和实际预约。网站的医院查询是文本检索，候选匹配必须有既有诊断或医生建议及公开专业依据，不能由症状推断诊断。

用户应能完成：找到医院 → 收藏与对比 → 查看准备步骤 → 下载资料清单 → 区分服务与医疗／行程预算 → 找到真实联系方式。服务端模式还应能提交咨询，并由管理员持续管理补充资料、接诊确认、服务报价、行程、就诊和随访。

不以“页面有按钮”代表功能完成。关键路径必须实际可操作，保存必须经服务端验证并能再次读取，公开预览必须明确显示其能力边界。

## 2. 现有能力与缺口

| 环节 | 原有能力 | 缺少内容 | 本轮实施 |
|---|---|---|---|
| 了解医院 | 九家医院、科室与专家、官方来源、城市地图、八语搜索 | 多院对比、收藏、失效资料解释 | 最多三院对比、会话内收藏、核查日期与未知项 |
| 决定下一步 | 有依据的候选探索 | 从查到医院到实际出行之间的引导 | 六阶段攻略、十二项准备清单、官方资源 |
| 准备资料 | 服务端病情和检查意见录入 | 用户不知道向医院提供什么、问什么 | 下载通用准备清单与空白病情摘要模板；公开站不收病历文件 |
| 费用决策 | 1,000–10,000 美元纯服务费 | 容易误解为全部费用，缺少自填预算 | 服务费范围＋用户自填医疗、交通、住宿、其他预算的算术工具 |
| 跨境沟通 | 公开邮箱、服务端偏好语言 | 真实联系方式集中说明、时差 | 联系页、北京时间与用户选择时区对照、隐私与一般咨询入口 |
| 信任判断 | 有来源，未说明合作／接诊关系 | 数据核查机制、信息纠错、签约主体提示 | 资料透明页、核查日期、明确未知项、公开纠错邮箱入口 |
| 运营履约 | 新咨询到关闭的粗粒度状态、内部备注 | 接诊证明、预约院区、书面报价、下一行动及到期日期 | 加密协调计划、运营工作台、待办与资料核查列表 |

## 3. 本轮网站信息架构

- 医院目录：搜索、城市二级页、医院详情、收藏／对比入口。
- 就医指南：了解资源、准备资料、等待确认、准备出行、在华就诊、回国衔接；勾选进度仅保留在当前标签页，刷新会清除。
- 实用工具：费用规划、清单／空白摘要下载、对比入口。金额为 USD，医疗和行程预算为空时不能显示成“已覆盖的总价”。
- 服务与费用：沿用纯服务费范围；所有交付范围、期限、次数、取消退款在付款前书面确认。
- 联系我们：一般咨询邮箱、时区对照、隐私请求与纠错入口。邮件入口不预填病情、证件或患者个人资料。
- 资料透明：目录范围、官方依据、核查日期、来源与临床匹配的区别。运营品牌不等于经营主体登记信息。

所有新增客户界面提供中文、英语、法语、日语、韩语、印地语、泰语、印尼语。保留原始医院名称；不伪造多语门诊、合作、号源或英语服务。

## 4. 后台协调流程

保留原有新咨询、已联系、等材料、等医院确认、关闭、归档状态，增加预约已确认、在华就诊、随访。

每条咨询增加独立协调计划：

1. 七项工作核对：资料、医院回复、书面服务范围、行程、到院、出院资料、随访衔接。
2. 下一行动和日期，用于工作台显示到期／逾期项目；不自动发送通知或联系客户。
3. 医院确认状态、医院编号、预约日期和北京时间、实际院区／地点及确认凭据。未具备这些资料不能保存为“已确认”。
4. 具体服务报价及对应书面范围。金额须落在配置的服务费范围内，医疗费和行程费不合并进平台服务报价。内部记录不是自动生成的合同，也不代表客户已付款。
5. 记录与原咨询一起加密、使用同一访问权限、版本冲突和保留／删除政策。普通跟进保存不能清除已有协调计划。

资料核查工作台列出历史资料、超过 90 天的临床介绍、未发布条目与缺少当前接诊确认的信息。90 天只是运营复核阈值，不是医疗质量认证。

## 5. 数据、隐私与部署

| 数据 | 存放位置 | 是否进入公开托管 |
|---|---|---|
| 医院、公开科室／专家、官方来源 | 种子 JSON、运行目录及审核后公开快照 | 是 |
| 八语攻略、通用资料模板、界面代码 | 版本库、公开静态资源 | 是 |
| 收藏医院 ID、清单勾选、自填预算 | 当前标签页内存 | 否，不发送服务器，刷新清除 |
| 病情、联系方式、内部报价／协调记录 | 本机或未来正式服务端的加密数据库 | 否 |
| 密钥、管理员密码、部署授权 | 本机私有路径／环境配置 | 否 |

Cloudflare Pages 继续承载公开网站。本机 Python／SQLite 承载完整管理后台。未部署安全服务端前，不将公开咨询表单伪装为已开通，不通过 URL、邮件预填或第三方分析服务传递病情。

正式接收真实在线咨询还需：稳定 HTTPS 服务端、持久加密存储与独立密钥备份、真实经营主体与个别服务协议、服务语言和排班人员、医院逐案确认渠道、可执行的退款和删除流程。代码可以实现流程，不能替经营者编造这些事实。

## 6. 后续增量的优先级与条件

| 优先级 | 功能 | 启动条件 |
|---|---|---|
| 下一步 | 把现有后台部署到受保护的正式环境 | 已取得云服务授权、域名及真实运营／隐私配置 |
| 下一步 | 扩充医院与国际患者入口、门诊渠道、院区 | 每一条有官方证据、核查日期与人工复核负责人 |
| 有真实咨询后 | 安全病历上传 | 私有对象存储、短期签名、类型／大小限制、恶意文件检测、细粒度授权、保留与删除实现 |
| 有稳定履约后 | 客户私有进度页面 | 患者身份校验、访问撤销、日志与数据隔离；不能仅凭回执编号公开查询 |
| 有真实交易后 | 支付与退款 | 主体、合同、商户账号、价格与退款规则已确认；不直接收取医院医疗费 |
| 有医院授权后 | 预约接口或转诊合作 | 医院正式授权和可验证接口；不抓取或虚构号源 |
| 有随访团队后 | 远程复诊／健康建议 | 医疗机构、医生资质和适用司法辖区已核实；不由平台自行诊断 |

当前不引入用户社区、评论排名、诊断聊天机器人、自动签证承诺、全包医疗定价和支付墙。这些能力不解决首批获客与协调的主要缺口，且依赖尚未具备的真实业务条件。

## 7. 验收与发布

- 九家医院的简称、科室、专家与已收录诊疗词检索回归通过；不把不同医院混同。
- 收藏上限、移除、对比、语言切换和返回目录均可用，医院 ID 不是公开患者信息。
- 清单进度、下载与打印可操作；下载不包含用户未提交的病情、邮箱或内部记录。
- 预算以分为单位计算，拒绝负数／非数值；空白费用保持“待确认”，不输出伪装成医院报价的总价。
- 后台验证已确认预约所需字段、报价范围、版本冲突、鉴权与加密；旧咨询可继续读取和修改。
- 八语缺词、占位符、宽屏与手机宽度、键盘操作及脚本错误检查。
- 打包只包含公开文件，核查无密钥、运行数据库、测试患者、内部记录。
- 部署完成后以实际网址验证资源和关键路径；无法取得 Cloudflare 发布授权时保留可审查的本机版本和发布包，并明确线上尚未更新。
